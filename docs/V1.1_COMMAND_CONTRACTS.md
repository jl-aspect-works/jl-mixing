# JL Mixing Automation v1.1 Command Contracts

**Status:** Approved and scope-frozen

## 1. Shared command behavior

### 1.1 Context discovery

Commands resolve context using explicit paths first and marker-based upward discovery second. They do not rely on removed lifecycle directories or folder names alone.

### 1.2 Validation before mutation

Mutating commands:

1. Parse and validate all arguments.
2. Resolve and validate governing records.
3. Validate cross-document and filesystem invariants.
4. Build the proposed mutation in memory or staging.
5. Validate generated JSON/Markdown.
6. Commit atomically or with rollback-capable coordinated replacement.

### 1.3 Dry-run

A dry-run:

- Performs relevant read-only validation.
- Shows resolved values and planned mutations.
- Creates no persistent UUIDs or timestamps.
- Does not modify files, directories, manifests, or shell state.
- Returns the validation outcome the real command would return.

### 1.4 Exit codes

```text
0  success
1  general/operational error
2  argument error
3  configuration/runtime dependency error
4  context-resolution error
5  validation error
6  unsafe filesystem operation
```

### 1.5 Helpful next steps

Creation and workflow commands retain concise, context-aware `Next:` guidance with directly usable commands. Paths are safely shell-quoted.

## 2. `new-studio`

### 2.1 Syntax

```text
new-studio [options]

--root PATH          Workspace root (default: ~/Music/Mixes)
--name NAME          Studio name (default: Mixing Studio)
--engineer NAME      Default mix engineer
--sample-rate HZ     Default sample rate (default: 48000)
--bit-depth BITS     Default bit depth (default: 24)
--file-format FORMAT WAV or AIFF (default: WAV)
--default-cd         Enable automatic directory changes by default
--no-default-cd      Disable automatic directory changes by default
--dry-run            Show the planned workspace without creating it
-h, --help           Show command help
```

Environment override:

```text
JL_MIXING_ROOT
```

Precedence: explicit `--root`, environment override, built-in default.

### 2.2 Removed options

- `--daw`
- `--non-interactive`

Known removed options receive targeted v1.1 diagnostics.

### 2.3 Behavior

Creates only:

```text
<Root>/
├── Clients/
└── Studio/
    └── studio.json
```

The destination must not exist as a file, directory, or symlink. No merge, adoption, or repair is allowed.

The command validates all options before writes, stages/validates `studio.json`, and removes only the newly created root if creation fails.

`new-studio` never changes directory itself.

### 2.4 Success output

```text
Studio created successfully.

Root:          /Users/jake/Music/Mixes
Studio:        Mixing Studio
Engineer:      Jake
Audio format:  48000 Hz / 24-bit / WAV
Configuration: /Users/jake/Music/Mixes/Studio/studio.json
Automatic directory change: disabled

Next:
  new-client <client-id>
```

Dry-run labels the next command as `After creation:`.

## 3. `new-client`

### 3.1 Syntax

```text
new-client CLIENT_ID [options]

--name NAME             Display name
--artist NAME           Default artist or program name
--sample-rate HZ        Default project sample rate
--bit-depth BITS        Default project bit depth
--file-format FORMAT    WAV or AIFF
--delivery-method TEXT  Default delivery method
--deliverables LIST     Comma-separated requested deliverables
--cd                    Enter the new client directory
--no-cd                 Remain in the current directory
--dry-run               Show the planned client without creating it
-h, --help              Show command help
```

### 3.2 Removed options

- `--revision-limit`
- `--non-interactive`

### 3.3 Defaults

- `--name` defaults to a title-cased form of `CLIENT_ID`.
- Audio and delivery defaults inherit from `studio.json` unless explicitly overridden.
- `artist` may be empty.
- Deliverable parsing splits on commas, trims values, rejects empty/unknown/duplicate values, and preserves order.

### 3.4 Creation

Creates:

```text
Clients/<Sanitized Client Name>/
├── client.json
└── Projects/
```

Preflight checks:

- Valid studio context and schema.
- Valid strict client slug.
- Non-empty display name.
- Safe readable folder name.
- Case-insensitive ID and folder collision checks.
- Nonexistent destination.
- Writable `Clients/` directory.

Creation is staged and committed as one client directory. A failed post-creation `cd` does not roll back the client.

### 3.5 Directory behavior

`--cd` and `--no-cd` are mutually exclusive and cannot be combined with `--dry-run`.

Precedence:

1. Explicit option.
2. Studio CLI preference.
3. Built-in false.

### 3.6 Success guidance

Without automatic directory change:

```text
Next:
  cd '/Users/jake/Music/Mixes/Clients/Acme Records'
  new-mix --project "PROJECT NAME"
```

After a successful wrapper `cd`:

```text
Next:
  new-mix --project "PROJECT NAME"
```

## 4. `new-mix`

### 4.1 Syntax

```text
new-mix --project PROJECT_NAME [options]

--client ID_OR_PATH      Client ID or client-directory path
--project NAME           Project display name (required)
--project-id ID          Stable project slug; derived by default
--artist NAME            Artist or program name
--album TITLE            Album or collection title
--producer NAME          Producer name
--engineer NAME          Mix engineer
--bpm NUMBER             Tempo
--key TEXT               Musical key
--time-signature TEXT    Time signature
--sample-rate HZ         Project sample rate
--bit-depth BITS         Project bit depth
--file-format FORMAT     WAV or AIFF
--deadline YYYY-MM-DD    Project deadline
--deliverables LIST      Comma-separated requested deliverables
--description TEXT       Creative direction
--source PATH            Initial client-delivery file or directory
--cd                     Enter the project directory after creation
--no-cd                  Remain in the current directory
--dry-run                Show the planned project without creating it
-h, --help               Show command help
```

### 4.2 Removed options

- `--project-type`
- `--daw`
- `--template`
- `--non-interactive`

### 4.3 Client resolution

Resolve client by:

1. Explicit `--client` stable ID.
2. Explicit client path.
3. Unambiguous current-directory client context.

A command outside a client context without `--client` fails with a useful example.

### 4.4 Default precedence

1. Explicit `new-mix` option.
2. Client default.
3. Studio default.
4. Empty/null where permitted.

Specific rules:

- Artist: option, client default, then empty.
- Engineer: option, studio default, then empty.
- BPM: option or null.
- Key/time signature: option or empty; no assumed `4/4`.
- Audio: option, client default, studio default.
- Delivery method: client default, studio default; there is no project-level `--delivery-method` override.
- Requested deliverables: option, client default, studio default.
- Deadline: option or null.
- Creative direction: option or empty.

### 4.5 Creation

Creates the full canonical project tree immediately. It creates no initial revision directory and no delivery manifest.

`--source` behavior:

- Accepts an existing regular file or directory.
- Copies, never moves or modifies, source content into `Original_Delivery/`.
- Preserves filenames and directory structure.
- Rejects symlinks and unsafe/colliding destination paths.
- A source-copy failure rolls back the entire project.

The complete project is built in a temporary sibling directory, validated, and atomically committed.

Initial state:

```json
{
  "current_revision": 0,
  "approved_revision": null,
  "delivered_revision": null
}
```

### 4.6 Success guidance

```text
Next:
  cd '/path/to/project'
  new-revision --description "Initial mix"
```

When the wrapper enters the project, omit the `cd` line.

## 5. `validate-intake`

### 5.1 Syntax

```text
validate-intake [options]

--project PATH             Explicit project path
--source PATH              Intake source directory
--expected-sample-rate HZ  Override expected sample rate
--expected-bit-depth BITS  Override expected bit depth
--no-duplicate-check       Skip duplicate-basename detection
--dry-run                  Build and print a temporary report
-h, --help                 Show command help
```

### 5.2 Removed options

- `--report-only`
- `--non-interactive`

### 5.3 Functional boundary

Preserve v1.0.4 functionality. Do not expand audio QC in v1.1.

Preserved behavior:

- Default source: `01_Client_Files/Original_Delivery/`.
- Recursive regular-file inventory.
- Case-insensitive duplicate-basename detection unless disabled.
- Audio-candidate extensions exactly:
  - `.wav`
  - `.wave`
  - `.aif`
  - `.aiff`
  - `.flac`
  - `.mp3`
  - `.m4a`
- Opportunistic `ffprobe` use when installed.
- Existing sample-rate/bit-depth comparisons and technical reporting.
- Existing unreadable candidate-audio blocking errors.
- Existing unsupported/non-audio extension warnings.
- No new `ffmpeg` decode check, exact-content duplicate hash, dual-mono detection, container validation, or deeper stream analysis.

### 5.4 Report behavior

The command writes a clearer managed section containing:

- Intake summary.
- Critical errors.
- Duplicate filenames.
- Project-format mismatches.
- Unsupported/non-audio files.
- Skipped or unavailable checks.
- Source inventory.
- Preparation recommendations.

Only the exact automated section is replaced. Content outside it is preserved byte-for-byte.

A completed normal scan updates the report even when blocking errors exist. Blocking errors return exit `5`; warnings alone do not.

Dry-run prints the proposed managed section and does not update the report.

### 5.5 Next guidance

Success:

```text
Next:
  Review 00_Admin/Intake_Report.md
  Prepare accepted audio in 02_Audio_Preparation/Working_Audio/
```

Blocking findings:

```text
Next:
  Review and resolve the critical errors in 00_Admin/Intake_Report.md
```

## 6. `new-revision`

### 6.1 Syntax

```text
new-revision [options]

--project PATH         Explicit project directory
--description TEXT     Revision description
--source PATH          Mix-print file or directory to copy
--cd                   Enter the new revision directory
--no-cd                Remain in the current directory
--dry-run              Show the planned revision without creating it
-h, --help             Show command help
```

### 6.2 Description defaults

- Revision 1: `Initial mix`.
- Later revisions: `Revision N`.
- Explicit whitespace-only descriptions are rejected.

### 6.3 Numbering and validation

Next number:

```text
state.current_revision + 1
```

Folder format uses at least two digits:

```text
Revision_01
Revision_10
Revision_100
```

Before creation, verify:

- Revision records are contiguous and ascending.
- `current_revision` equals the highest record.
- Every record has its expected directory.
- No case-insensitive variant of the next directory exists.

No inconsistency is silently repaired.

### 6.4 Source behavior

- A regular file is copied into the revision root.
- A source directory contributes its immediate eligible files only.
- Nested directories, symlinks, unsupported object types, and case-insensitive collisions are rejected.
- A source file named `Revision_Notes.md` is rejected.
- Source files are copied, never moved or modified.
- No audio decoding or technical inspection is performed.

Without `--source`, the revision contains only `Revision_Notes.md`.

### 6.5 Mutation

Append a revision record, update `current_revision`, and update `last_modified_at`.

Preserve:

- `approved_revision`
- `delivered_revision`

The directory and manifest mutation commit together. Failure leaves neither a record nor a directory.

### 6.6 Success guidance

```text
Next:
  approve-mix
```

Client review transfer is manual and occurs before the user runs `approve-mix`.

## 7. `approve-mix`

### 7.1 Syntax

```text
approve-mix [options]

--project PATH       Explicit project directory
--revision NUMBER    Revision to approve; defaults to current
--approved-by NAME   Approver identity; defaults to Client
--date TIMESTAMP     ISO-8601 approval time; defaults to current time
--dry-run            Show the approval change without modifying it
-h, --help           Show command help
```

### 7.2 Removed options

- `--notes`
- `--non-interactive`

### 7.3 Validation

- Require at least one revision.
- Selected revision must exist and have its expected directory.
- Approver must contain non-whitespace text.
- Approval timestamp must be valid and cannot precede revision creation.
- Approval does not require mix-print files, a delivery package, technical inspection, or proof that files were sent.

### 7.4 Mutation

- Set `state.approved_revision` to the selected revision.
- Populate/replace approval metadata on the selected record.
- Preserve `current_revision` and `delivered_revision`.
- Preserve historical approval metadata on other revisions.
- Reapproving a previously approved but currently unapproved revision replaces that revision’s old approval metadata.

Approving the already-approved revision is a rejected no-op, even if new approver/date arguments are supplied.

### 7.5 Output

Successful approval always points to:

```text
Next:
  create-delivery
```

If an existing final delivery represents a different revision, warn that `create-delivery` will require explicit replacement authorization.

## 8. `create-delivery`

### 8.1 Syntax

```text
create-delivery [options]

--project PATH          Explicit project directory
--include PATTERN       Include matching revision files; repeatable
--exclude PATTERN       Exclude matching revision files; repeatable
--working-prefix TEXT   Exclude basenames beginning with the prefix
--overwrite             Replace same-shape tracked generated content
--clean                 Destructively replace all final-delivery contents
--zip                   Create the delivery ZIP
--dry-run               Show the planned package without creating it
-h, --help              Show command help
```

### 8.2 Removed options

- `--revision`
- `--checksum`
- `--mark-delivered`
- `--non-interactive`

### 8.3 Approved revision

The source revision is always `state.approved_revision`. To deliver another revision, approve it first.

`create-delivery` does not require the approved revision to equal the current revision.

### 8.4 File selection

Source directory:

```text
04_Revisions/Revision_NN/
```

Selection rules:

- Immediate regular files only.
- Exclude `Revision_Notes.md`.
- Reject symlinks and subdirectories as deliverables.
- No extension allowlist.
- Include/exclude patterns preserve v1.0.4 basename glob semantics.
- Includes are applied first; excludes afterward.
- Working-prefix filtering uses the basename.
- Empty patterns/prefixes are rejected.
- At least one selected file is required.

Every selected file is packaged, even when its name is unrecognized.

### 8.5 Classification and placement

Best-effort whole-word/phrase matching treats spaces, hyphens, and underscores as equivalent for matching only.

Precedence:

```text
stems
instrumental
acapella
tv_mix
performance_mix
master
main_mix
unclassified
```

Only `stems` files are placed under `Stems/`. Every other file is placed in the delivery root. Source basenames are preserved exactly.

### 8.6 Hashing and staging

For each selected source:

1. Hash source with SHA-256.
2. Copy into same-filesystem staging.
3. Hash staged destination.
4. Require hashes to match.
5. Record staged size and hash.

Generate and validate the delivery manifest only after all copies verify.

### 8.7 Replacement modes

#### Default

Reject existing package conflicts.

#### `--overwrite`

- Replace matching generated files and the manifest.
- Preserve `Delivery_Notes.md` and untracked content.
- Replace the deterministic generated ZIP when requested.
- Reject if files tracked by the previous manifest would become stale and remain outside the new manifest.
- Require a valid prior manifest for tracked-package replacement.

#### `--clean`

- Explicitly authorizes removal of every file, directory, and symlink entry inside `05_Final_Delivery/`.
- Does not require a valid prior manifest.
- Never follows symlinks.
- Recreates `Stems/` and a fresh `Delivery_Notes.md`.
- Dry-run lists every item that would be deleted and prominently warns that the operation is destructive.

`--overwrite` and `--clean` are mutually exclusive.

### 8.8 ZIP

When `--zip` is requested, create:

```text
05_Final_Delivery/<project-id>-delivery.zip
```

Preserve broad v1.0 behavior:

- Recursively include the current staged delivery-directory contents.
- Exclude only the ZIP being created.
- Include manifest, notes, deliverables, stems, and preserved user-added files present in the staged package.
- Do not list the ZIP in the delivery manifest.
- ZIP failure aborts the complete transaction.

### 8.9 Commit

The staged delivery directory and updated project manifest commit as one rollback-capable transaction.

On success:

- `state.delivered_revision = state.approved_revision`.
- `metadata.last_modified_at` updates.
- `current_revision` and `approved_revision` remain unchanged.

On failure, restore the prior package and project manifest.

### 8.10 Final guidance

Without ZIP:

```text
Next:
  Transfer the contents of 05_Final_Delivery using the configured delivery method.
```

With ZIP:

```text
Next:
  Transfer <project-id>-delivery.zip using the configured delivery method.
```

JL Mixing does not claim that transfer occurred.

## 9. Shell integration

### 9.1 Supported commands

Wrappers are defined for:

- `new-client`
- `new-mix`
- `new-revision`

### 9.2 Communication channel

The wrapper creates a secure temporary result file and invokes the real executable with an internal environment variable such as:

```text
JL_MIXING_CD_RESULT_FILE
```

The executable writes one absolute committed destination only after successful creation and only when a directory change is requested.

The wrapper:

- Uses `command <name>` to avoid recursion.
- Never parses human-readable output.
- Never uses `eval`.
- Validates one absolute existing-directory result.
- Performs `builtin cd -- "$destination"`.
- Prints `Entered:` only after successful `cd`.
- Cleans temporary state on success, failure, and interruption.
- Preserves creation failure status.
- Returns an operational error when creation succeeded but `cd` failed.

## 10. `install.sh`

### 10.1 Syntax

```text
./install.sh [options]

--prefix PATH             Installation prefix (default: ~/.local)
--no-shell-integration    Do not modify shell startup configuration
-h, --help                Show command help
```

Environment override:

```text
JL_MIXING_INSTALL_PREFIX
```

Precedence: explicit option, environment, default.

### 10.2 Installed layout

```text
PREFIX/
├── bin/
│   ├── new-studio
│   ├── new-client
│   ├── new-mix
│   ├── validate-intake
│   ├── new-revision
│   ├── approve-mix
│   ├── create-delivery
│   ├── jl-mixing-shell-integration
│   └── jl-mixing-uninstall
└── share/
    └── jl-mixing/
        ├── application
        ├── schemas
        ├── templates
        ├── packaging
        ├── .venv
        └── install-state.json
```

Do not install `complete-project`. Remove a legacy launcher only when it carries the JL Mixing managed marker.

### 10.3 Dependencies

Required at installation:

- Bash.
- Python 3.10+ and venv support.
- `jq`.

Command-specific tools such as `ffprobe` and ZIP tooling are checked only when needed.

Use the pinned private virtual environment and preserve offline vendor-wheel behavior.

### 10.4 Managed shell block

By default, detect zsh or bash and update one user-level startup file block:

```bash
# >>> JL Mixing managed configuration >>>
export PATH="/absolute/prefix/bin:$PATH"

if command -v jl-mixing-shell-integration >/dev/null 2>&1; then
    source "$(command -v jl-mixing-shell-integration)"
fi
# <<< JL Mixing managed configuration <<<
```

Rules:

- Back up before modification.
- Preserve outside content byte-for-byte.
- Replace one valid existing block in place.
- Reject malformed or duplicate markers.
- Never modify system-wide shell files.
- `--no-shell-integration` leaves shell files unchanged and prints manual PATH guidance.

### 10.5 Transaction

Stage and verify application, venv, launchers, integration, and uninstaller before commit. Coordinate backups and rollback for application files, launchers, and shell configuration.

Help performs no dependency check, filesystem mutation, or network access.

## 11. `jl-mixing-uninstall`

### 11.1 Syntax

```text
jl-mixing-uninstall [options]

--prefix PATH    Installation prefix
-h, --help       Show command help
```

The installed launcher supplies its prefix for normal use.

### 11.2 Behavior

- Read/validate `install-state.json` when available.
- Validate managed launchers and shell markers before removal.
- Move managed files to same-prefix backup staging before final deletion.
- Remove the managed shell block.
- Remove workflow launchers and shell integration.
- Remove the application directory.
- Remove `jl-mixing-uninstall` last.
- Preserve prefix parent directories used by other applications.
- Preserve all studio workspaces and project data.

If shell cleanup cannot be performed safely, abort without removing the active installation.

If state is missing, fall back conservatively and remove a shell block only when unambiguous.

## 12. v1.0 compatibility diagnostics

All v1.1 workflow commands reject v1.0 schemas and recognizable legacy layouts before mutation.

Known removed options receive targeted argument-error messages. Truly unknown options use the normal unknown-option error.

Removed command:

```text
complete-project
```

There are no hidden compatibility aliases.
