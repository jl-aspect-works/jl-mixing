# JL Mixing Automation v1.1 Design Specification

**Status:** Approved and scope-frozen  
**Baseline:** JL Mixing Automation v1.0.4  
**Target release:** 1.1.x  
**Workspace compatibility:** Fresh v1.1 workspace required

## 1. Purpose

JL Mixing Automation v1.1 simplifies the studio workspace and project workflow while preserving useful v1.0.4 behavior that was not explicitly changed.

The release removes project lifecycle folders, removes JL-managed DAW/template behavior, establishes strict v1.1 data models, improves transactional safety, and adds optional automatic directory changes for creation commands.

## 2. Governing principles

1. Preserve unrelated v1.0.4 behavior unless this specification explicitly changes it.
2. Treat source client files and DAW content as user-owned or opaque.
3. Never silently repair inconsistent state.
4. Validate before mutation and commit related filesystem/JSON changes transactionally.
5. Never silently delete unknown content except when the user explicitly authorizes destructive `create-delivery --clean` behavior.
6. Keep user-visible behavior within this approved scope. Newly discovered user-visible requirements return to design review.
7. All new or materially changed code must contain clear explanatory comments.

## 3. Scope

### 3.1 Included

- Flattened client project layout.
- Removal of active/completed project lifecycle management.
- Removal of JL Mixing DAW, template, and preset management.
- Strict v1.1 studio, client, snapshot, project, and delivery schemas.
- Three-pointer project workflow state.
- Revised command contracts for all supported workflow commands.
- Transactional creation, approval, delivery, install, upgrade, and uninstall behavior.
- Optional automatic `cd` behavior for `new-client`, `new-mix`, and `new-revision`.
- Automatic shell integration through one managed shell-startup block.
- Clearer managed output in `Intake_Report.md` while preserving v1.0.4 intake-validation functionality.
- A fresh-workspace compatibility boundary between v1.0 and v1.1.

### 3.2 Explicitly excluded or deferred

- Migration of v1.0 workspaces.
- Automatic archive or long-term project cleanup.
- `complete-project`, `reactivate-project`, or other lifecycle commands.
- Cancelled, abandoned, or on-hold project statuses.
- JL-managed DAW project templates, presets, or DAW metadata.
- A `create-review` command.
- Expanded intake audio QC beyond v1.0.4.
- New full-file `ffmpeg` decode checking.
- Exact-content SHA-256 duplicate detection during intake.
- Exact dual-mono detection.
- New container/stream analysis or additional `ffprobe` fields.
- A v1.1 delivery-history archive.
- A project/client editing command.
- Continuous delivery-file monitoring.

Deferred features remain in the version-agnostic future-features backlog and are not assigned to a release unless explicitly approved later.

## 4. Canonical workflow

```text
new-studio
    ↓
new-client
    ↓
new-mix
    ↓
validate-intake
    ↓
new-revision
    ↓
Send revision files to the client manually
    ↓
approve-mix
    ↓
create-delivery
```

Workflow meanings:

- `new-revision` creates the next working revision.
- Client review transfer is manual and is not represented as final delivery.
- `approve-mix` records which revision was approved.
- `create-delivery` builds the single authoritative final-delivery package from the approved revision.
- “Delivered” means a validated final-delivery package was generated. It does not assert that an external transfer occurred.

## 5. Workspace layout

The default root remains:

```text
~/Music/Mixes/
```

Canonical top-level structure:

```text
~/Music/Mixes/
├── Clients/
└── Studio/
    └── studio.json
```

Removed top-level concepts:

```text
DAWs/
Archive/
```

Canonical client structure:

```text
Clients/<Sanitized Client Name>/
├── client.json
└── Projects/
```

Canonical project structure:

```text
Clients/<Client>/Projects/<Sanitized Project Name>/
├── 00_Admin/
│   ├── project-manifest.json
│   ├── client-profile-snapshot.json
│   ├── Intake_Report.md
│   └── Project_Notes.md
├── 01_Client_Files/
│   ├── Original_Delivery/
│   ├── References/
│   └── Documentation/
├── 02_Audio_Preparation/
│   ├── Working_Audio/
│   ├── Rejected_Files/
│   └── Preparation_Report.md
├── 03_DAW_Project/
├── 04_Revisions/
│   └── Revision_NN/
│       ├── Revision_Notes.md
│       └── <mix-print and related files>
├── 05_Final_Delivery/
│   ├── Stems/

└── 06_Recall/
    ├── Recall_Sheet.md
```

Key changes from v1.0:

- Projects live directly under `Projects/`; there is no `Active/` or `Completed/` layer.
- `03_DAW_Project/Project/` is removed; `03_DAW_Project/` is the opaque DAW boundary.
- `Revision_NN/Prints/` is removed; revision files live directly in `Revision_NN/`.
- Project paths remain stable throughout the workflow.

## 6. Ownership model

### 6.1 JL Mixing-managed metadata

- `Studio/studio.json`
- `client.json`
- `00_Admin/project-manifest.json`
- `00_Admin/client-profile-snapshot.json`
- `05_Final_Delivery/delivery-manifest.json`
- Generated final-delivery files
- Installed launchers, shell integration, and installation-state metadata

### 6.2 User-managed content

- `Project_Notes.md`
- `Preparation_Report.md`
- `Revision_Notes.md`
- `Delivery_Notes.md`
- `Recall_Sheet.md`
- `01_Client_Files/References/`
- `01_Client_Files/Documentation/`
- `02_Audio_Preparation/Working_Audio/`
- `02_Audio_Preparation/Rejected_Files/`
- `06_Recall/`

### 6.3 Shared managed Markdown

`Intake_Report.md` is shared. JL Mixing owns only the exact section between:

```text
<!-- BEGIN AUTOMATED SECTION -->
<!-- END AUTOMATED SECTION -->
```

Content outside those markers is preserved byte-for-byte. Missing, duplicated, nested, or reversed markers are rejected during a normal update; they are not repaired automatically.

### 6.4 Immutable or opaque boundaries

- `01_Client_Files/Original_Delivery/` is immutable client source. JL Mixing may explicitly copy into it and inspect it, but never modifies original files.
- `03_DAW_Project/` is fully opaque and user/DAW-owned. JL Mixing creates the boundary and may verify that it exists, but does not interpret, clean, rename, or modify its contents.
- Native DAW templates and presets remain outside JL Mixing.

### 6.5 Symlink and cleanup rules

- Commands do not intentionally follow symlinks across ownership boundaries.
- Rollback removes only content created by the current command or content explicitly authorized for replacement.
- Unknown content is not silently removed except by explicit `create-delivery --clean`, whose approved meaning is complete replacement of all contents inside `05_Final_Delivery/`.

## 7. Identity and naming

Client and project identity each use three distinct concepts:

1. Stable machine-facing ID.
2. Human-readable display name.
3. Readable sanitized folder name.

IDs:

- Lowercase ASCII slugs.
- Allowed characters: `a-z`, `0-9`, `-`.
- Must begin and end with an alphanumeric character.
- Consecutive hyphens are rejected.
- Immutable after creation.

Folder names:

- Derived from the display name.
- Filesystem-safe and readable.
- Unsafe separators/control characters are replaced or removed.
- Trailing spaces and periods are removed.
- Reserved or empty results are rejected.
- Numeric suffixes are never added automatically.

Collision rules:

- Client IDs and client folder names are unique case-insensitively across `Clients/`.
- Project IDs and project folder names are unique case-insensitively within the owning client.
- Delivery destination paths are unique case-insensitively.
- Lookup uses stable IDs and marker-based context, not folder names alone.

## 8. Project state model

Canonical state:

```json
{
  "state": {
    "current_revision": 0,
    "approved_revision": null,
    "delivered_revision": null
  }
}
```

Meanings:

- `current_revision`: highest successfully created revision; never decreases.
- `approved_revision`: currently approved revision; may point to any existing revision and may move backward.
- `delivered_revision`: revision represented by the current authoritative final delivery; may move backward after explicit replacement.

Derived stages:

- **Setup:** `current_revision == 0`
- **In progress:** `current_revision != approved_revision`
- **Approved:** `current_revision == approved_revision` and `delivered_revision != current_revision`
- **Delivered:** all three pointers are equal and a structurally valid matching delivery manifest exists

Rules:

- `new-revision` increments `current_revision` and preserves approval/delivery pointers.
- `approve-mix` may approve any existing revision without moving `current_revision`.
- `create-delivery` always packages `approved_revision` and, on success, sets `delivered_revision` to it.
- Inconsistent state fails validation; no command silently repairs it.

## 9. Revision model

Canonical revision record:

```json
{
  "number": 1,
  "revision_id": "UUID",
  "created_at": "ISO-8601 date-time",
  "description": "Initial mix",
  "approval": {
    "approved_at": null,
    "approved_by": null
  }
}
```

Revision rules:

- Records are ascending, contiguous, and append-only after successful creation.
- Only approval fields are mutable.
- `approval` is always present; fields are both null or both populated.
- Status is derived:
  - approved when `number == approved_revision`
  - open when `number == current_revision` and not approved
  - superseded otherwise
- Reapproving a previously approved but currently unapproved revision replaces that revision’s approval metadata.
- Approving the already-approved revision is a rejected no-op.

## 10. Intake validation boundary

`validate-intake` preserves v1.0.4 functionality. v1.1 reorganizes report presentation and adapts paths, but does not expand audio QC.

Preserved behavior:

- Recursive regular-file inventory.
- Case-insensitive duplicate-basename warnings.
- Audio-candidate extensions:
  - `.wav`
  - `.wave`
  - `.aif`
  - `.aiff`
  - `.flac`
  - `.mp3`
  - `.m4a`
- Opportunistic `ffprobe` inspection when available.
- Existing sample-rate and bit-depth comparisons.
- Existing channel-count and duration reporting when available.
- Existing unreadable candidate-audio errors.
- Existing unsupported/non-audio extension warnings.
- No `ffmpeg` decode expansion, exact-content hashing, dual-mono analysis, container validation, or new stream analysis.

## 11. Final delivery model

There is one authoritative final-delivery directory:

```text
05_Final_Delivery/
```

`create-delivery`:

- Always uses the approved revision.
- Considers immediate regular files in the approved revision directory.
- Excludes `Revision_Notes.md`.
- Uses no extension allowlist.
- Applies the preserved include, exclude, and working-prefix filters.
- Packages every selected file even when its filename does not match a known convention.
- Preserves source basenames exactly.
- Uses best-effort filename classification.
- Places only classified stems in `Stems/`; all other files remain in the delivery root.
- Computes mandatory SHA-256 hashes and verifies each staged copy against its source.
- Generates an immutable delivery manifest.
- Optionally creates a broad recursive ZIP using preserved v1.0 behavior.

Best-effort classification order:

1. `stems`
2. `instrumental`
3. `acapella`
4. `tv_mix`
5. `performance_mix`
6. `master`
7. `main_mix`
8. `unclassified`

Spaces, hyphens, and underscores are equivalent for matching only. Actual filenames are never renamed.

Replacement modes:

- Default: reject replacement conflicts.
- `--overwrite`: replace matching generated files, preserve other content, and reject a replacement that would leave stale previously tracked files.
- `--clean`: explicitly remove every file, directory, and symlink entry inside `05_Final_Delivery/`, then rebuild it. The directory itself remains. Symlinks are removed as links and are never followed.

All replacement modes are rollback-capable. A failed operation leaves the previous package and project state recoverable.

## 12. Automatic directory changes

`new-client`, `new-mix`, and `new-revision` support:

```text
--cd
--no-cd
```

Studio default:

```json
{
  "cli": {
    "change_directory_after_create": false
  }
}
```

Precedence:

1. Explicit `--cd` or `--no-cd`
2. `studio.json` preference
3. Built-in default `false`

A normal executable cannot change its parent shell. JL Mixing therefore installs shell wrappers automatically through a managed `.zshrc` or `.bashrc` block. The executable decides whether a directory change is requested; the wrapper performs the actual parent-shell `cd` after successful creation.

If shell integration is unavailable, creation still succeeds and the command prints a safely quoted copy-and-paste `cd` command.

## 13. Installer and uninstaller

Default prefix:

```text
~/.local
```

Installed structure:

```text
PREFIX/
├── bin/
│   ├── workflow launchers
│   ├── jl-mixing-shell-integration
│   └── jl-mixing-uninstall
└── share/
    └── jl-mixing/
        ├── application files
        ├── schemas/
        ├── templates/
        ├── .venv/
        └── install-state.json
```

Installer behavior:

- Supports `--prefix` and `--no-shell-integration`.
- Uses one `PREFIX/bin` PATH entry.
- Automatically adds/updates one managed user-level shell block by default.
- Supports zsh and bash.
- Preserves everything outside the managed block.
- Rejects malformed or duplicate managed markers.
- Stages and verifies the complete application before replacing an active installation.
- Rolls back application files, launchers, shell integration, and shell configuration together on failure.
- Never modifies studio workspaces.

Uninstaller behavior:

- Removes only JL-managed files and the exact managed shell block.
- Uses `install-state.json` to identify configured shell state.
- Removes the uninstaller last.
- Is rollback-capable.
- Never removes studio workspaces, projects, audio, or user notes.

## 14. v1.0 compatibility boundary

v1.1 requires a newly created workspace.

All v1.1 commands reject:

- v1.0 schema records.
- Recognizable legacy structures such as `DAWs/`, `Projects/Active/`, `Projects/Completed/`, `03_DAW_Project/Project/`, and `Revision_NN/Prints/`.

Commands do not:

- Rewrite v1.0 JSON.
- Move legacy projects.
- Flatten legacy folders.
- Adopt an existing v1.0 root.
- Offer automatic repair or migration.

Installing v1.1 does not alter existing v1.0 workspaces.

## 15. Exit-code compatibility

Preserve the v1.0.4 shared exit-code categories:

```text
0  success
1  general/operational error
2  argument error
3  configuration/runtime dependency error
4  context-resolution error
5  validation error
6  unsafe filesystem operation
```

A valid dry-run returns the same validation outcome the real command would return without performing mutations.

## 16. Quality gates

Required release gates:

```bash
shellcheck bin/* lib/*.sh install.sh uninstall.sh
make test
make strict-test
make release-check
```

Testing must include:

- All schemas and cross-document invariants.
- Command happy paths and failures.
- Dry-run non-mutation.
- Transaction rollback and failure injection.
- User-owned content preservation.
- Destructive `--clean` authorization.
- Shell integration in zsh and bash.
- Installer upgrade/reinstall/uninstall transactions.
- Full canonical workflow.
- v1.0 workspace rejection.

Tests use isolated temporary homes, roots, prefixes, and shell startup files. They never touch the developer’s real workspace or shell configuration.

## 17. Authority order

When implementation details conflict, use:

1. Approved v1.1 design documents.
2. Final v1.1 schemas.
3. Command tests.
4. Existing v1.0.4 behavior for anything not explicitly changed.

Rejected or superseded conversational proposals are not requirements.
