# JL Mixing Automation v1.1 Data Model

**Status:** Approved and scope-frozen  
**Schema draft:** JSON Schema Draft 2020-12

## 1. Schema set

```text
schemas/
├── studio.schema.json
├── client.schema.json
├── client-profile-snapshot.schema.json
├── project-manifest.schema.json
└── delivery-manifest.schema.json
```

All schemas:

- Require the canonical top-level fields.
- Use `additionalProperties: false` at every defined object level.
- Fix `metadata.schema` and `metadata.schema_version` with `const`.
- Require UUID document identifiers.
- Require ISO-8601 date-time values for stored timestamps.
- Require `created_with` in the form `jl-mixing 1.1.x`.
- Reject unknown v1.0 fields rather than ignoring them.
- Are loaded from the installed application and never downloaded.

## 2. Common metadata rules

Mutable governing documents use:

```json
{
  "metadata": {
    "schema": "document-schema-name",
    "schema_version": "1.1.0",
    "document_id": "UUID",
    "created_with": "jl-mixing 1.1.0",
    "created_at": "ISO-8601 date-time",
    "last_modified_at": "ISO-8601 date-time"
  }
}
```

Immutable snapshots use the same structure without `last_modified_at`.

Rules:

- `document_id` is immutable and unique studio-wide.
- `created_with` is immutable.
- `created_at` is immutable.
- `last_modified_at` changes only after a successful document mutation.
- Dry-runs, no-ops, and failed transactions do not change timestamps.
- `created_by` is removed from all v1.1 documents.

## 3. `studio.json`

Location:

```text
Studio/studio.json
```

Canonical structure:

```json
{
  "metadata": {
    "schema": "mixing-studio",
    "schema_version": "1.1.0",
    "document_id": "11111111-1111-4111-8111-111111111111",
    "created_with": "jl-mixing 1.1.0",
    "created_at": "2026-07-14T20:00:00-04:00",
    "last_modified_at": "2026-07-14T20:00:00-04:00"
  },
  "studio_id": "mixing-studio",
  "studio_name": "Mixing Studio",
  "root_path": "/Users/jake/Music/Mixes",
  "defaults": {
    "mix_engineer": "Jake",
    "audio": {
      "sample_rate": 48000,
      "bit_depth": 24,
      "file_format": "WAV"
    },
    "delivery": {
      "method": "Cloud transfer",
      "requested_deliverables": [
        "main_mix",
        "instrumental"
      ]
    }
  },
  "cli": {
    "change_directory_after_create": false
  }
}
```

Rules:

- `root_path` is the resolved absolute workspace root.
- `studio_id` is a stable slug.
- `studio_name` contains non-whitespace text.
- `mix_engineer` may be empty.
- Supported sample rates remain the v1.0.4 supported set.
- Supported bit depths remain `16`, `24`, and `32`.
- `file_format` is `WAV` or `AIFF`.
- Delivery method is non-empty.
- Requested deliverables are non-empty and unique.
- `change_directory_after_create` defaults to `false`.
- There is no `default_daw` or other DAW/template configuration.

## 4. `client.json`

Location:

```text
Clients/<Client>/client.json
```

Canonical structure:

```json
{
  "metadata": {
    "schema": "mixing-client",
    "schema_version": "1.1.0",
    "document_id": "22222222-2222-4222-8222-222222222222",
    "created_with": "jl-mixing 1.1.0",
    "created_at": "2026-07-14T20:05:00-04:00",
    "last_modified_at": "2026-07-14T20:05:00-04:00"
  },
  "client_id": "acme",
  "client_name": "Acme Records",
  "defaults": {
    "artist": "The Example Band",
    "audio": {
      "sample_rate": 48000,
      "bit_depth": 24,
      "file_format": "WAV"
    },
    "delivery": {
      "method": "Cloud transfer",
      "requested_deliverables": [
        "main_mix",
        "instrumental"
      ]
    }
  }
}
```

Rules:

- `client_id` is an immutable lowercase slug.
- `client_name` is the trimmed human-readable name.
- `defaults.artist` may be empty.
- Audio and delivery defaults are copied from `studio.json`, then overridden by explicit `new-client` options.
- Client defaults are snapshots; later studio-default changes do not update existing clients.

## 5. `client-profile-snapshot.json`

Location:

```text
00_Admin/client-profile-snapshot.json
```

Canonical structure:

```json
{
  "metadata": {
    "schema": "mixing-client-profile-snapshot",
    "schema_version": "1.1.0",
    "document_id": "33333333-3333-4333-8333-333333333333",
    "created_with": "jl-mixing 1.1.0",
    "created_at": "2026-07-14T20:10:00-04:00"
  },
  "source_client": {
    "client_document_id": "22222222-2222-4222-8222-222222222222",
    "client_id": "acme",
    "client_name": "Acme Records"
  },
  "defaults": {
    "artist": "The Example Band",
    "audio": {
      "sample_rate": 48000,
      "bit_depth": 24,
      "file_format": "WAV"
    },
    "delivery": {
      "method": "Cloud transfer",
      "requested_deliverables": [
        "main_mix",
        "instrumental"
      ]
    }
  }
}
```

Rules:

- The snapshot has its own UUID; it does not reuse the client UUID.
- `source_client.client_document_id` and `client_id` match the owning client record.
- Values are copied exactly at project creation.
- The snapshot is immutable and has no `last_modified_at`.
- Later client changes do not update existing snapshots.
- A missing, malformed, or mismatched snapshot invalidates the project.
- Project-manifest project settings remain authoritative for actual project operation.

    "current_revision": 0,
    "approved_revision": null,
    "delivered_revision": null

### 6.1 Removed project fields

The v1.1 manifest has no:

- `project_type`
- `daw`
- Stored lifecycle status
- Stored folder paths
- Revision status
- Revision folder
- Revision `created_by`

Paths and statuses are derived.

### 6.2 Field rules

- `project_id` and `project_name` are immutable.
- Client identity fields match the owning `client.json` and snapshot.
- `artist` is required and non-empty after default resolution.
- `album`, `producer`, and `mix_engineer` may be empty.
- `music.bpm` is a positive number or null.
- `music.key` may be empty.
- `music.time_signature` may be empty; v1.1 does not assume `4/4`.
- Audio fields use the supported enums.
- Delivery method is non-empty.
- Requested deliverables are a non-empty unique array.
- Deadline is a valid date or null.
- Creative direction is required but may be empty.

### 6.3 Requested-deliverable enum

Retain the existing planning enum:

```text
main_mix
instrumental
acapella
tv_mix
performance_mix
stems
master
```

This array is informational. Delivery packaging is not restricted to requested types.

## 7. Project state and revision invariants

### 7.1 State pointers

- `current_revision` is `0` or an existing revision number.
- `approved_revision` is null or an existing revision number.
- `delivered_revision` is null or an existing revision number.
- `current_revision` equals the highest revision record.
- Revision numbers are ascending and contiguous from `1`.
- `current_revision` never decreases.

### 7.2 Revision record

```json
{
  "number": 3,
  "revision_id": "55555555-5555-4555-8555-555555555553",
  "created_at": "2026-07-20T11:00:00-04:00",
  "description": "Final vocal balance",
  "approval": {
    "approved_at": "2026-07-20T14:00:00-04:00",
    "approved_by": "Client"
  }
}
```

Rules:

- `revision_id` is unique studio-wide.
- `description` is non-empty.
- Approval fields are both null or both populated.
- Approval time cannot precede revision creation.
- Revisions are append-only except for approval fields.

### 7.3 Derived stages

```text
Setup       current_revision == 0
In progress current_revision != approved_revision
Approved    current_revision == approved_revision
            and delivered_revision != current_revision
Delivered   current_revision == approved_revision
            and approved_revision == delivered_revision
            and the matching delivery manifest is structurally valid
```

## 8. `delivery-manifest.json`

Location:

```text
05_Final_Delivery/delivery-manifest.json
```

Canonical structure:

```json
{
  "metadata": {
    "schema": "mixing-delivery",
    "schema_version": "1.1.0",
    "document_id": "66666666-6666-4666-8666-666666666666",
    "created_with": "jl-mixing 1.1.0",
    "created_at": "2026-07-20T15:30:00-04:00"
  },
  "project": {
    "project_document_id": "44444444-4444-4444-8444-444444444444",
    "project_id": "blue-sky",
    "project_name": "Blue Sky"
  },
  "client": {
    "client_document_id": "22222222-2222-4222-8222-222222222222",
    "client_id": "acme"
  },
  "revision": {
    "number": 3,
    "revision_id": "55555555-5555-4555-8555-555555555553",
    "description": "Final vocal balance",
    "approval": {
      "approved_at": "2026-07-20T14:00:00-04:00",
      "approved_by": "Client"
    }
  },
  "delivery": {
    "method": "Cloud transfer"
  },
  "files": [
    {
      "path": "Blue Sky Main Mix.wav",
      "deliverable_type": "main_mix",
      "size_bytes": 104857600,
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
    },
    {
      "path": "BlueSky_NoVox.wav",
      "deliverable_type": "unclassified",
      "size_bytes": 101234567,
      "sha256": "abcdef0123456789abcdef0123456789abcdef0123456789abcdef0123456789"
    },
    {
      "path": "Stems/Blue Sky Stem Drums.wav",
      "deliverable_type": "stems",
      "size_bytes": 53428800,
      "sha256": "2222222222222222222222222222222222222222222222222222222222222222"
    }
  ]
}
```

### 8.1 Metadata

The delivery manifest is immutable. Replacement creates:

- A new document UUID.
- A new creation timestamp.
- A new immutable snapshot.

There is no `last_modified_at`, `created_by`, `delivered_at`, `delivered_by`, or free-form notes field.

### 8.2 Project, client, and revision snapshots

- Project identity matches the project manifest.
- Client identity matches the project manifest and owning client.
- Revision number and UUID identify the approved revision used for the package.
- Revision description and approval are copied as immutable snapshots.
- Revision approval fields are non-null in a delivery manifest.

### 8.3 Delivery object

```json
{
  "delivery": {
    "method": "Cloud transfer"
  }
}
```

The method is copied from the project manifest. It records the planned transfer method and does not prove external handoff.

### 8.4 File records

Each delivered file record contains exactly:

```text
path
deliverable_type
size_bytes
sha256
```

Rules:

- `path` is relative to `05_Final_Delivery/`.
- Paths use `/` separators.
- Paths are not absolute and contain no `.` or `..` segments.
- Paths resolve to regular files, not symlinks.
- Paths are unique case-insensitively.
- `size_bytes` is a non-negative integer from the staged destination.
- `sha256` is 64 lowercase hexadecimal characters from the staged destination.
- At least one file record is required.
- Source paths are not stored.
- Basenames are preserved exactly.

### 8.5 Deliverable-type enum

```text
stems
instrumental
acapella
tv_mix
performance_mix
master
main_mix
unclassified
```

Classification is best-effort and never affects file eligibility.

Matching treats spaces, hyphens, and underscores as equivalent separators and uses whole words/recognized phrases. Classification precedence is the enum order shown above.

Recognized phrases include:

- `stem` or `stems`
- `instrumental`
- `acapella`, `a cappella`, `a-cappella`, or `a_cappella`
- `tv mix`, `tv-mix`, or `tv_mix`
- `performance mix`, `performance-mix`, or `performance_mix`
- `master`
- `main mix`, `main-mix`, or `main_mix`

Files without a recognized phrase are `unclassified` and remain in the delivery root.

### 8.6 Inventory exclusions

The `files` array does not include:

- `delivery-manifest.json`
- `Delivery_Notes.md`
- ZIP files
- Checksum sidecars
- Temporary/staging files

### 8.7 Deterministic ordering

- Types present in `project-manifest.delivery.requested_deliverables` follow that array’s order.
- Remaining types follow classifier precedence.
- Files within a type sort case-insensitively by relative path.

### 8.8 Structural versus full integrity validation

Routine structural validation checks:

- Schema validity.
- Matching project/client/revision identities.
- `revision.number == state.delivered_revision`.
- Safe unique paths.
- Listed files exist as regular files.
- Valid size/hash field formats.
- At least one file.

Routine validation does not recalculate hashes.

Full integrity verification recalculates file sizes and SHA-256 during:

- `create-delivery`.
- Explicit future integrity tooling, if separately approved.
- Tests.

## 9. Cross-document invariants

Application validation enforces relationships not fully expressible in JSON Schema:

1. Every document UUID is unique studio-wide.
2. Client references match `client.json`.
3. Snapshot source identity matches `client.json` and the project manifest.
4. Project revision records are contiguous and match revision directories.
5. State pointers reference existing revisions.
6. The approved revision record contains approval metadata.
7. The delivery manifest matches the project, client, delivered revision, and revision UUID.
8. Delivery manifest approval matches the revision snapshot used at package creation.
9. Every listed delivery file exists and remains inside `05_Final_Delivery/`.
10. Case-insensitive IDs, folder names, and manifest paths are unique in their required scopes.
11. A non-null delivered pointer without a valid matching manifest is invalid.
12. A delivery manifest without the matching project delivered pointer is invalid.
13. Recognizable v1.0 layouts are rejected.

## 10. Markdown templates

```text
templates/
├── Intake_Report.md
├── Project_Notes.md
├── Preparation_Report.md
├── Revision_Notes.md
├── Delivery_Notes.md
└── Recall_Sheet.md
```

### 10.1 Intake report

```markdown
# Intake Report

<!-- BEGIN AUTOMATED SECTION -->
No intake validation has been run.
<!-- END AUTOMATED SECTION -->
```

Only the automated section is JL-managed.

### 10.2 Project notes

```markdown
# Project Notes
```

### 10.3 Preparation report

```markdown
# Preparation Report
```

### 10.4 Revision notes

```markdown
# Revision {{REVISION_NUMBER}} Notes

Description: {{REVISION_DESCRIPTION}}
```

Placeholders are resolved only at creation. The resulting file is then user-managed.

### 10.5 Delivery notes

```markdown
# Delivery Notes
```

Preserved by `--overwrite`; recreated by `--clean`.

### 10.6 Recall sheet

```markdown
# Recall Sheet
```

All generated Markdown is UTF-8 with a final newline. Missing templates or unresolved placeholders fail before commit.

## 11. Installation-state record

Location:

```text
PREFIX/share/jl-mixing/install-state.json
```

Canonical concept:

```json
{
  "installation_prefix": "/Users/jake/.local",
  "shell_integration": {
    "enabled": true,
    "shell": "zsh",
    "startup_file": "/Users/jake/.zshrc"
  }
}
```

This internal record contains installation mechanics only. It contains no studio or project data and enables conservative uninstall cleanup.
